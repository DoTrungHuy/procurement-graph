# 使用与人工检查指南

第一次操作请先看[新手操作指南](user-guide.md)。本页用于熟悉系统后的逐项功能复查。

本指南按当前2.4.0界面编写。模型抽取是否启用以“连接设置”为准，只有选择“模型抽取”并提交任务才会使用模型服务；以下检查使用已有结果、解析预检和历史响应回放，无需新模型请求。“公告核验样本”含20篇公告、26个采购包、138条商品和123条投标记录。以下固定数字仅用于该数据集；自己导入数据后应以导入范围为准。

页面能操作、业务结果正确、达到比赛要求是三种不同结论。本指南检查操作流程，并提供原文比对办法；历史响应、构造案例和自动测试不能代替独立人工准确率验证。

## 1. 确认服务与数据集

1. 打开 `http://127.0.0.1:5173/#/overview`。
2. 左下角应显示“本地服务已连接”。
3. 点击“连接设置”，核对版本为2.4.0、状态为“本地服务正常”。“模型服务”可填写地址、名称和API Key，保存后供新任务使用，刷新或重启后保留。Key留空保留原值且不回显；保存本身不请求模型。未启用访问保护时，“服务访问令牌”留空；启用后填写管理员提供的系统令牌，不填写模型Key。详细说明见[模型配置](model-settings.md)。
4. 关闭设置，把顶部数据集切换为“公告核验样本”。
5. 工作台应显示20篇公告、26个采购包、138条标的。采购包多于公告是正常的一篇多包情况。

如果页面显示113个供应商，这是去重后的投标主体数量；123指投标记录数，两者不同不表示数据丢失。

可直接查看 `http://127.0.0.1:8000/api/health`，检查 `version` 为 `2.4.0`，`model_network_enabled` 与保存的模型启用状态一致。它只读取服务状态，不执行模型抽取。

异常判断：空白页、持续无法连接、已选公告核验样本却显示空数据、数据集切换后仍显示上一数据集的结果，都应记录。固定数字不同先检查数据集和筛选条件，不直接判定数据丢失。

## 2. 检查项目检索与详情

1. 在工作台搜索框输入“肇庆学院”，点击“查询”。
2. 应找到“肇庆学院新校区理科实训楼等楼宇信息化建设项目”下的合同包1。
3. 点击项目名称打开“采购包详情”。
4. 核对下面的当前样本值：

| 字段 | 当前样本值 |
|---|---|
| 采购单位 | 肇庆学院 |
| 采购包 | 合同包1（信息化平台及网络机房建设） |
| 中标供应商 | 广东南方通信建设有限公司 |
| 中标金额 | 10,719,988元 |
| 竞标结果记录 | 20条 |

5. 切换“标的明细”“竞标结果”，检查表格内容随标签变化。
6. 在标的明细点击“来源”，应打开单独的来源面板。
7. 按一次Esc应关闭来源面板，采购包详情仍在；再按一次Esc应关闭采购包详情。
8. 清空搜索条件，点击查询，项目总数应恢复26，翻页应显示不同记录。

原文对照文件：[肇庆学院公告](../demo/procurement/data/demo/html/t20260809_27099966.html)。当前样本值用于检查平台是否稳定复现；还应对照原文，不能仅因为界面数字相同就确认抽取完全正确。

审查核对时，明确未通过者应保留原始记录并排除有效共同竞标。原文未披露审查结果不等于明确失败；中标、专家评分等其他证据可能证明有效参与，不能只看“未披露”三个字判断是否计入。

## 3. 检查商品筛选与原文证据

1. 左侧进入“标的检索”。
2. 先点“重置”，在“规格型号”中只填写 **MES3200**，点击“检索”。输入时不带格式符号；提交时会清理型号首尾的空格和反引号。
3. 应找到“智慧工厂管理系统”，当前记录为：

| 字段 | 当前记录 |
|---|---|
| 品目 | 工业控制用计算机系统 |
| 品牌 | 科瑞特 |
| 型号 | MES3200 |
| 数量 | 1 |
| 单价 | 358,000元 |
| 总价 | 358,000元 |

4. 点击“查看原文”，检查来源文件为 `t20260807_27093889.html`，定位对应这条商品，不能跳到另一件商品的证据。
5. 在品牌、品目等筛选项中选择相符值，再检索，目标记录应仍存在。
6. 展开“金额与数量筛选”，设置单价下限400000、上限300000。点击检索，应提示“筛选下限不能大于上限”，不能报整页错误或清空数据库。
7. 点击“重置”，应恢复138条商品。
8. 搜索不存在的型号，应显示空结果；清空条件后应恢复数据。

原文对照文件：[广东科学技术职业学院公告](../demo/procurement/data/demo/html/t20260807_27093889.html)。在文件中查找 `MES3200` 或“智慧工厂管理系统”。

已发现的问题：原文数量为 `1.0000(套)`，当前记录数量为1，但 `quantity_unit` 为空。数量数值和金额一致，辅助计量单位未完整保留，应登记为待修复，不能把这条样本的所有信息都判为正确。

## 4. 检查五个关系场景

保持数据集为“公告核验样本”。进入“关系分析”，在每个场景点击“填入样本示例”，再点击“查询关系”。该按钮只填条件，仍需点击查询。

| 场景 | 示例主体 | 当前预期结果 |
|---|---|---|
| 合作画像 | 香港城市大学(东莞) | 4家中标供应商；产品品牌分组为5项 |
| 投标活跃度 | 香港城市大学(东莞) | TOP5列表有5项；当前5项参与频次均为1；共同出现组合有10项 |
| 竞争关系 | 中国移动通信集团广东有限公司 | TOP5有5项，全部参与方28项 |
| 共同采购单位 | 北京纳凯诺科技发展有限公司、广东写川技术有限公司 | 返回香港城市大学(东莞)；合作次数合计2，已披露金额632,400元 |
| 共同竞标项目 | 中国电信股份有限公司广东分公司、中国移动通信集团广东有限公司 | 返回2个采购包、来自2篇公告；已披露金额14,307,988元 |

合作画像的4家中标商与当前金额：广州市晞灵国际贸易有限公司883,800元，广东写川技术有限公司448,500元，广州健星仪器有限公司189,600元，北京纳凯诺科技发展有限公司183,900元。

共同竞标的2个项目是肇庆学院信息化建设项目和民众街道民众分局视频监控运维升级改造项目。可以从结果打开采购包，回到竞标详情检查两家公司及其有效参与依据。

每个场景还应检查：

- 图表和完整明细表格同时展示，切换结果分组后两者对应同一份结果；金额指标、分页和详情入口仍可用。
- 关系网络默认可见，按当前数据集及采购包数展示，不随场景查询主体变化；核对数据集切换、拖动缩放及点击采购包打开详情。
- “产品品牌”与“中标供应商”是不同口径，不能把品牌当成投标公司。
- 修改主体后应清除旧结果或等待重新查询，不能把上一个主体的结果当成新主体结果。
- “共同采购单位”允许两家公司分别中标不同采购包；“共同竞标项目”要求它们在同一个采购包有效参与。
- 金额未披露应显示“未披露”，不能因为缺失就认为报价为0。

这些数量是当前样本的回归参照；并非官方隐藏评测的答案或成绩。

## 5. 使用新增的层级核验

入口：工作台 → 点击采购项目 → 采购包详情 → 层级核验。

该页目前是自动规则结果与原文核查页，不是人工编辑或审批工作流。没有手动改字段、点击“确认通过”并保存的功能。

三个计数的含义：

| 计数 | 含义 |
|---|---|
| 原文记录 | 该包保留下来的全部商品披露行 |
| 明细视图 | 仅折叠已确认摘要之后，仍用于该视图的行数 |
| 待核验关联 | 已发现候选关联，但没有通过全部检查的组数 |

当前限制：2026-10-16实时读取“公告核验样本”的26个采购包时，候选、已确认和待核验关联均为0。该样本主要用于公告正文回放，没有专门覆盖跨文件摘要与明细。因此看到“暂未发现可核验的摘要与明细关联”是正常空态，不能凭这个空态宣称确认、拒绝分支都已验证。

遇到候选关系时：

1. 查看摘要引用了哪一个附件，是否明确为“本项全部明细”等完整范围。
2. 展开“核验依据”，逐项看通过或待核验原因。
3. 分别点击“查看摘要原文”“查看明细原文”。有新定位数据时，面板还会显示“程序定位的原文行”。
4. 核对包号、供应商、下级业务编号、原文总价和引用范围。
5. 仅当所有条件通过才应显示“包含关系已确认”；只凭合计金额相同不能确认。
6. 有失败检查时应显示“保留全部原文行”，明细视图不应因此少行。

专用构造案例的判定标准：

| 案例 | 输入 | 正常行为 |
|---|---|---|
| 可确认包含 | 教学设备摘要100元，明确引用完整附件；电脑60元、交换机40元，编号、原文与供应商均一致 | 原文3行、明细视图2行；摘要仍可查看；仅明细视图折叠摘要 |
| 供应商冲突 | 同一组数据，但电脑记录的供应商与摘要不一致 | 原文3行、明细视图3行；供应商检查待核验；不折叠摘要 |
| 金额相同但缺少范围证据 | 合计仍为100元，原文没有完整包含说明 | 保留全部行，不能因金额相同自动确认 |

案例为自动测试构造，不是官方公告，也不能证明真实数据准确率提升。规则详细条件见[摘要与明细核验](item-hierarchy.md)。

## 6. 检查三表下载

先使用顶部“导出三表”，在Excel中打开：

- Sheet名和顺序应为“总表”“标的表”“投标人表”。
- 在未修改的公告核验样本中，不含表头分别是26、138、123行。
- UUID和采购包应能对应；不要把一篇多包公告误判为重复公告。
- 页面金额为元，标准工作簿为万元。例如商品单价358000元导出为35.8万元，Excel格式可能显示35.80。
- 总表中标金额、投标报价按万元保留两位小数。例如10719988元在总表按模板显示1072.00万元，属于模板精度换算。
- 未披露字段留空，不能为了蓝色必需列就自行补值。

再从层级核验页点击“下载当前数据集的明细三表”：它导出整个当前数据集，不只是当前打开的采购包。没有已确认包含关系时，两份三表的业务单元格应一致，不要求ZIP字节或生成时间相同。

在专用构造案例中，默认原文三表保留摘要，明细三表才折叠已确认摘要；“总表”和“投标人表”不因商品分层改变。严格比赛三表导出不启用 `include_notes=true`，因为该参数会增加内部处理说明页。

## 7. 检查数据接入，不调用模型

这一部分会把处理记录和回放结果写入所选数据集。当前“官方基准数据”为空，可用于本次小样本操作；不要误以为切换标签会自动导入官方全量数据。

1. 顶部切换为“官方基准数据”，工作台应显示空数据。
2. 进入“数据接入” → “核验样本” → “下载样本公告”。得到只含20篇样本公告的ZIP。
3. 选择“上传文件”，处理方式选“解析预检”，上传刚下载的ZIP，点击“开始处理”。
4. 等待结束：进度到20/20，模型请求为0。预检只验证输入可解析，不生成商品抽取结果，所以空数据集仍应没有新增商品。
5. 再将处理方式改为“历史响应回放”，使用相同ZIP提交，或到“核验样本”点击“回放核验样本”。
6. 结束后检查模型请求仍为0；首次回放可看到历史响应缓存命中。若已经复用入库结果，缓存命中可能为0，应结合“已复用结果”判断。
7. 回工作台，当前数据集应有20篇公告、26个采购包、138条商品。
8. 回到处理记录，下载“此批三表”和“此批处理说明”，确认是刚才批次，不是其他数据集的全部结果。
9. 完成后切回“公告核验样本”，继续其他检查。

“完成，有处理说明”不自动等于程序失败；应展开说明判断是原文缺失、输入问题还是处理失败。“成功”也不等于附件和全部字段完全正确。

任意新文件没有历史响应时，回放失败是预期行为，不会转成模型请求。该20篇ZIP只验证正文流程，不能用于确认扫描件、旧Office、复杂附件的完整处理能力。以下免费操作检查采用预检和回放，不需要模型抽取或官方全量ZIP。

## 8. 运行自动回归

如果希望自己复现，所有命令在项目根目录执行。已有依赖已安装，无需再次Setup；缺少浏览器组件时再按实际报错准备。

```powershell
# 后端全部测试，使用隔离测试库
.\demo\procurement\.venv\Scripts\python.exe -X utf8 -m pytest -q demo/procurement/backend/tests

# 生成当前前端构建
npm --prefix demo/procurement/frontend run build

# 原有页面、交互边界与层级核验分别检查
node scripts/verify_frontend.mjs --production
node scripts/verify_frontend_edgecases.mjs
node scripts/verify_item_hierarchy.mjs
node scripts/verify_model_settings.mjs
```

依次执行，上一条成功后再执行下一条。当前版本的预期分别为185项后端测试、18组主界面、7组交互边界、5组层级核验、5组模型配置检查通过；以后增加测试后数字可以变化。主界面检索检查含复制型号时的空格、反引号清理及中标供应商搜索。层级核验脚本使用构造案例；模型配置脚本使用假Key、独立配置文件和禁止模型请求的测试服务，检查刷新及重启后的持久性，均不修改当前主系统。

脚本默认使用Playwright安装的浏览器。如果缺少浏览器组件，在项目根目录准备测试依赖：

```powershell
npm --prefix scripts ci
.\scripts\node_modules\.bin\playwright.cmd install chromium
```

需要使用自定义浏览器时，可按实际安装位置设置 `PLAYWRIGHT_EXECUTABLE_PATH`，见[开发说明](development.md)。自动回归使用隔离数据库、空凭据或假Key及禁止真实模型请求的设置，不改变主系统的模型开关。

验证记录位置：

- `docs/verification`：随源码保留的既有验证记录。
- `results/ui-checks/latest`：本机最近的主界面和交互结果。
- `results/ui-hierarchy/<时间>/verification.json`：本次层级核验结果。
- 同一层级测试目录下的 `hierarchy-confirmed.png`、`hierarchy-mobile.png`：构造案例截图。
- `results/model-settings-ui/<时间>/verification.json`：模型配置持久性结果及桌面、手机截图。

## 9. 记录问题的方法

发现问题时记录数据集、页面、公告UUID、采购包、商品或主体、操作步骤、实际结果、预期结果和原文依据。例如：

```text
数据集：公告核验样本
公告：t20260807_27093889
商品：智慧工厂管理系统 / MES3200
操作：标的检索 -> 查看原文
实际：数量1，计量单位为空
原文：1.0000(套)
判断：数量数值正确，计量单位未完整保留
```

建议分别记录界面操作问题、统计口径问题、抽取信息缺失和缺少验证案例，避免把不同原因合成一个“功能不行”。当前仍需独立人工验证与真实平台验收，不能用自动测试通过数量代替比赛成绩。
