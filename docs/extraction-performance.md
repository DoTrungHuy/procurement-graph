# 提取恢复与性能验证

本候选在字段修复版本上保留 WorkBuddy JSON/SSE 接入与零积分校验，处理版本为 `package-v2.12`，解析格式仍为 `parse-v3.6`。原文解析、报价明细识别、来源定位、采购包对齐和标准三表继续执行。模型请求和解析的并发上限不增加。

## 三种附件优化

`EXTRACT_BLANK_TEMPLATES=true` 默认启用。只在完整解析文本匹配已核验的未填写模板、纯标题或自拟说明时省去模型请求；不会依据文件名或长度跳过。未知字词、填写值、金额、解析警告、混合内容和工作表标题均保持原流程。原文件、解析缓存和逐文件跳过依据保留。

`EXTRACT_STANDARD_TABLES=true` 默认启用。仅在公告包归属完整且唯一、整个附件都是明确的七字段表格、货币和数量单位明确、数值一致时直接按列读取。缺列、共享总价、复杂合并、并列货物、额外项目/投标信息或歧义会回退整个文件。该能力的实用覆盖必须由真实命中数说明。

`EXTRACT_BATCH_ATTACHMENTS=false` 默认关闭，供受控验证。每组 2—4 份、每份不超过 2500 字且合计不超过 8000 字，同一公告、公告已核验的唯一包，附件包号不得冲突。逐文件 ID、完整文本与来源独立；漏文件、重复 ID、跨来源、空结果、无法逐行核验的字段/数值、复杂评审结构会整组回退。异常后关闭本轮后续合批，防止重复消耗。零积分和凭据等致命错误直接停止，不以回退绕过。当前真实试跑未证明批处理收益，因此不默认开启。

三项开关都参与文件检查点及公告最终结果指纹。关闭全部开关时使用原来的逐文件流程。运行指标 `optimization_counts` 分别统计空模板、表格、批组、批文件、回退和实际批请求；`batch_disabled_reason` 记录停止合批的原因。

## 与本地全量比较

`scripts/compare_extraction_optimizations.py` 使用独立数据库和输出目录，对固定的本地全量 JSONL 逐公告比较七字段、来源、包与投标关系，保留重复记录的数量。先关闭三项新增优化做控制组，再同时开启做候选组，以区分先前字段修复和本次优化的影响。原始基线仅只读访问，比较前后检查 SHA256。

默认只回放已保存的原始响应；`--live-batches` 和 `--live-misses` 分别明确授权新合批请求、缺失缓存补跑。两者均强制检查上游报告零积分。凭据只从本机 `--profile` 读取，不进入报告。`--response-cache` 可添加其他只读响应层，所有新响应写到本轮目录。`MODEL_RESPONSE_CACHE_READ_DIRS` 使用系统路径分隔符；`MODEL_REPLAY_CHUNKING=auto` 按当前提示词的精确请求签名选择当前/历史分块，不能复用旧规则或旧最终预测。

此混合验证用于完整性、差异及请求数核对，不能把缓存回放时间和原来近一天的模型推理时间直接计算加速比，也不能称为官方准确率。

2026-10-17 本地 1038 篇全量比较见 [机器可读验证摘要](extraction-combined-validation.json)：已核验空模板 1448 份，响应处理次数由 11664 降到 10214，减少 12.431%。这包括缓存读取及受零积分约束的新请求，不是冷启动耗时加速比。标准七字段表格实际命中 0；合批 30 组均回退，因此批处理保持默认关闭。

与同代码、关闭新增优化的控制组相比，移除空模板来源生成的 35 条商品和 2 条投标记录；另 2 条商品仅因移除模板中的额外中标方而补全供应商，七字段和来源均未改。其余商品七字段及来源全部保留。与原本地全量相比的 7 篇继承差异单独列出，不计作本次优化收益，也不宣称通过官方验收。

在独立工作树做比较时，应显式复用基线的本地解析工具，并使用项目内短临时路径，避免 Windows 的归档成员路径限制：`--tools-root tools --work-root .cache/cmp-work`。本轮已对工具路径影响的 25 篇和长路径影响的 3 篇补跑，每篇最终结果均记录来源轮次；原全量的五个产物 SHA256 均保持不变。

## 分阶段限流

模型请求由独立信号量限制在 `MODEL_CONCURRENCY`，解析仍由 `PARSE_CONCURRENCY` 限制。公告在途数默认取两者之和且不超过 8，使等待解析的公告不占满模型调用机会。`NOTICE_CONCURRENCY` 设为 1—8 可显式限制在途公告；设为与 `MODEL_CONCURRENCY` 相同即可恢复原公告并发上限。默认 0 表示自动计算。

## 成功片段检查点

每份附件的文本块完成模型提取、来源核验及采购包对齐后，保存可丢弃的检查点。公告整体部分完成时，成功文本块可以复用，失败块继续重试。状态为部分完成的文本块不保存成成功检查点；解析警告仍会使公告进入待复核状态。

检查点指纹包含当前处理版本、提示词、模型与服务地址、输出和分块设置、完整解析文本、来源标签、公告上下文、回放文件列表，以及 RAG 知识库哈希。输入或规则变化会失效。校验和不匹配、缓存损坏或目录不可写时，回到原处理流程。缓存不会绕过回放模式禁止联网的约束。

默认目录为 `.cache/document-extractions`；`MODEL_DOCUMENT_CACHE_DIR` 可指定目录，设为空字符串可禁用。目录不进入 Git 和发布包。原始响应缓存与解析缓存继续独立保留；清空检查点后可以重新生成。

Compose 将检查点目录设为 `/app/data/.cache/document-extractions`，与现有业务数据卷一起保留。

运行指标新增 `document_cache_hits`、`document_cache_writes`，分别记录本轮实际复用及写入的文本块数。它们与原始响应命中、新模型请求分开计数。阶段计时现在也包含失败的解析和模型调用耗时，不能将多任务累计阶段时间当成墙钟时间。

## Word 表格

按 XML 单元格缓存已解析的文本与跨行合并关系，减少长合并单元格的重复回溯。保留 python-docx 的横向合并、跨行合并和省略单元格语义，以及原有 `TABLE/ROW/ITEM` 定位。没有提前丢弃声明、模板或混合报价附件，也没有减少扫描件 OCR。

## 验证方法

`scripts/benchmark_extraction_resume.py` 使用内置 20 篇公告的标识，读取本机对应原始公告与附件、既有原始模型响应，分别运行原公告上限且关闭检查点、自动在途上限且首次建立检查点、自动在途上限且复用检查点三轮。每轮使用独立数据库，明确禁止新模型调用，逐字段比较业务结果及三张导出表的单元格值。模型请求上限保持 4，解析上限保持 2。命令中的输出目录必须尚不存在：

```powershell
python scripts/benchmark_extraction_resume.py --original-run results/workbuddy-ds41-20261017 --official-data data/official-benchmark --parse-cache .cache/parsed --output results/resume-benchmark
```

这项验证测量已有解析缓存和历史响应条件下的重处理，不能代表首次完整推理、完整数据集速度或官方准确率。20 篇中的部分完成公告继续如实保留，不能用缓存命中代替质量验收。常规 Word 文件与长跨行合并表格的加速幅度应分别报告。
